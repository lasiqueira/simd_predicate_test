Branchless Conditionals and SIMD

How many "if / else" can a CPU actually do in one instruction?

I ran into this same idea three times in completely different contexts before it finally clicked: once in Game Engine Architecture (Jason Gregory), once in a PowerPC-assembly-to-C++ decompilation exercise, and again while going through Casey Muratori's Performance-Aware Programming course. This article is my attempt to write down the "aha" moment properly, and to back it up with actual measurements instead of just vibes.

1. A branchy conditional

Start with something completely ordinary. f64 here is just a double (64 bits): 

f64 cond(f64 a, f64 b)
{
    return a < b
        ? a + b
        : a * b - 2;
}

With optimizations on, a compiler will often turn this into something that behaves like the branchless version below. (The union is there because C++ doesn't let you apply bitwise operators like &, |, ~ directly to a double - so we reinterpret its bits through a union instead.) 

f64 cond2(f64 a, f64 b)
{
    union
    {
        f64 f;
        u64 u;
    } M, T, F, Result;

    M.u = (u64)0 - (u64)(a < b);
    T.f = a + b;
    F.f = a * b - 2;
    Result.u = (M.u & T.u) | (~M.u & F.u);
    return Result.f;
}

The interesting part: there is no branch in this code at all. You compute the "true" result, you compute the "false" result, and you use a bitmask to pick the correct one. That's the essence of branchless programming.

In more detail: if the condition is true, M.u becomes 0xFFFFFFFFFFFFFFFF (64 one-bits). ANDing that mask with T.u keeps every bit of the true result, while ANDing the inverted mask (all zero-bits) with F.u zeroes out the false result entirely - ORing them together just gives you back T. If the condition is false, it's the exact mirror image: M.u is all zeros, so the true result gets zeroed out and the inverted mask (all ones) passes the false result straight through.

A caveat worth being precise about: reading a union member other than the one most recently written - which is exactly what Result.f does after Result.u was set - is undefined behavior per the C++ standard, even though it's a very common pattern and GCC, Clang, and MSVC all explicitly document it as a supported extension. It's not the union itself that's the point of this article; it's the mask-and-select mechanism. If you'd rather have the exact same trick with no standard-based caveat at all, apply it to an integer type instead - &, |, and ~ work directly on it, no reinterpretation required: 

u64 cond2(u64 a, u64 b)
{
    u64 mask     = (u64)0 - (u64)(a < b);
    u64 trueRes  = a + b;
    u64 falseRes = a * b - 2;
    return (mask & trueRes) | (~mask & falseRes);
}

2. Why this unlocks something bigger

Once you know an if / else can be expressed purely with bitwise operations and no branch, it opens the door to something much more interesting on modern CPUs.

CPUs have evolved along (at least) two axes since the early days: cache hierarchies, and microarchitecture - specifically, register width. Cache is arguably the single most important topic for anyone writing performance-sensitive code, but that's a subject for another article.

On the register-width side: both x86-64 and ARM grew wider general-purpose registers over time, the same way "the NES is 8-bit, the SNES is 16-bit, the N64 is 64-bit" refers to register/bus width. Desktop and laptop CPUs went through the same evolution. The x86 accumulator is the classic example - it kept the same name lineage while growing wider, staying backwards compatible the whole way:

RegisterWidth
AL / AH8 bits
AX16 bits
EAX32 bits
RAX64 bits

Aside: one thing that causes real headaches is that the C++ ABI is not stable between Windows and Linux - compiling the same function signature for each platform can put parameters and return values in different registers entirely.

A double is 64 bits, which is already one of the widest primitive types you'll use day to day. But CPUs also have a separate family of registers built specifically for vector / SIMD work, wide enough to hold several 64-bit values at once. These are not a continuation of the AL/AX/EAX/RAX lineage - they're an entirely separate register file:

RegisterWidth
XMM128 bits
YMM256 bits
ZMM512 bits (rarer on personal machines - needs AVX-512)

Base SSE/AVX only give you 16 of these (XMM0-XMM15 / YMM0-YMM15). It's specifically AVX-512's encoding scheme that extends the register file to 32 (XMM0-31 / YMM0-31 / ZMM0-31).

3. Scaling the branchless trick across lanes

Here's the payoff: since a "return if / else" can be expressed as pure bit manipulation, you can do N of them at once, where N depends on how wide your registers are and how small your data type is.

With doubles: XMM gets you 2 at a time, YMM gets you 4, ZMM gets you 8. Switch to a single byte (uint8_t / char) instead, and the same 512-bit register can carry out 64 of these conditionals in one instruction:

TypeBitsXMM (128)YMM (256)ZMM (512)
double / uint64_t64248
float / uint32_t324816
uint16_t1681632
uint8_t (char)8163264

A compiler can sometimes auto-vectorize code like this on its own (more on exactly how reliable that is later), but writing it by hand with intrinsics guarantees it - including in unoptimized debug builds, where auto-vectorization never happens at all. That's what <immintrin.h> is for.

256-bit (4 doubles at a time)

__m256d cond256(__m256d a, __m256d b)
{
    __m256d mask = _mm256_cmp_pd(a, b, _CMP_LT_OQ);

    __m256d t = _mm256_add_pd(a, b);
    __m256d f = _mm256_sub_pd(
        _mm256_mul_pd(a, b),
        _mm256_set1_pd(2.0)
    );

    return _mm256_blendv_pd(f, t, mask);
}

512-bit (8 doubles at a time)

__m512d cond512(__m512d a, __m512d b)
{
    __mmask8 mask = _mm512_cmp_pd_mask(a, b, _CMP_LT_OQ);

    __m512d result = _mm512_sub_pd(
        _mm512_mul_pd(a, b),
        _mm512_set1_pd(2.0)
    );

    return _mm512_mask_add_pd(result, mask, a, b);
}

AVX-512 also introduces dedicated mask registers (__mmask8 here - one bit per 64-bit lane in a 512-bit register), which make this even more efficient. Instead of computing both results and blending them with a separate instruction, the mask is built once from a[i] < b[i] (one bit set per lane where it's true), and then folded directly into the arithmetic: result starts out holding the "false" answer (a * b - 2) for all 8 lanes, and _mm512_mask_add_pd overwrites only the lanes where the mask bit is set with a + b - so for a mask like T F F T T F F T, lanes 0, 3, 4 and 7 get replaced with a + b, and the rest keep the value already computed for the false case.

Of course, to actually feed these functions you need to load your data into the wide types too: 

std::vector<f64> lp512(std::vector<f64>& a, f64 b)
{
    std::vector<f64> res(a.size());

    __m512d wide_b = _mm512_set1_pd(b);

    for (size_t i = 0; i < a.size(); i += 8)
    {
        __m512d packed = _mm512_loadu_pd(&a[i]);
        __m512d condRes = cond512(packed, wide_b);
        _mm512_storeu_pd(&res[i], condRes);
    }

    return res;
}

4. Taking it further: 64 conditionals per instruction

Since the number of lanes scales inversely with element size, swapping double for uint8_t gets you from 8 lanes to 64 lanes in the same 512-bit register. The catch: a + b and a * b - 2 overflow trivially in an 8-bit range, and there's no native 8-bit SIMD multiply to begin with. The fix is to swap the arithmetic for saturating add/sub (clamped at 0/255 instead of wrapping), which is a real hardware feature for 8-bit lanes: 

u8 cond2(u8 a, u8 b)
{
    u8 mask = (u8)0 - (u8)(a < b);
    u8 trueRes = sat_add_u8(a, b);
    u8 falseRes = sat_sub_u8(sat_sub_u8(a, b), 2);
    return (u8)((mask & trueRes) | (~mask & falseRes));
}

__m512i cond512(__m512i a, __m512i b)
{
    __mmask64 mask = _mm512_cmp_epu8_mask(a, b, _MM_CMPINT_LT);

    __m512i falseRes = _mm512_subs_epu8(
        _mm512_subs_epu8(a, b),
        _mm512_set1_epi8(2)
    );

    return _mm512_mask_adds_epu8(falseRes, mask, a, b);
}

Same shape as before - build a mask, compute the false case, mask-overwrite with the true case - just now with a __mmask64 (one bit per byte lane) doing 64 conditionals per instruction instead of 8.

5. Does it actually matter in practice?

Talk is cheap, so this was measured: a 10,000,000-byte buffer, processed by a genuinely scalar loop, an AVX2 loop (32 lanes), and an AVX-512 loop (64 lanes), each run repeatedly for a few seconds and tracking the true minimum time (via a repetition tester built on RDTSC), on an AMD Ryzen 7 7800X3D. Both buffers were backed by Windows large pages and pre-touched, and the result buffers were pre-allocated outside the timed region, so the numbers below measure only the compute loop itself - no allocation, no page faults, no memory bandwidth surprises from cold memory.

ImplementationMin timeThroughputBandwidth
Scalar (bitmask) (MSVC, genuinely scalar)31.47 ms0.32 GOp/s0.30 GB/s
AVX2 (32 lanes)0.176 ms56.9 GOp/s53.0 GB/s
AVX-512 (64 lanes)0.174 ms57.5 GOp/s53.6 GB/s

Scalar (bitmask) to AVX2: roughly 179x faster. Scalar (bitmask) to AVX-512: roughly 181x. AVX2 to AVX-512 is basically a wash here (~1%). Part of the explanation is this specific CPU: Zen 4 (including the 7800X3D) implements AVX-512 by internally splitting each 512-bit operation into two 256-bit micro-ops ("double pumped") - full native 512-bit execution units didn't arrive until Zen 5, so a 512-bit op doesn't get twice the ALU work done per cycle the way you might expect. But that alone doesn't fully explain a ~1% difference (as section 6 will show, AVX-512 does have a real edge once you isolate it) - the bigger factor here is that this particular workload (10MB in, 10MB out) is bound by L3 cache/store bandwidth rather than compute once vectorized at all (this CPU's 96MB 3D V-Cache comfortably holds the whole working set, so it never touches DRAM), which swamps any compute-side difference between the two. A good reminder that "wider SIMD" only pays off up to whatever the next bottleneck happens to be - and right now, for this data size, that bottleneck is memory, not the ALU.

Notice AVX-512 isn't just tied with AVX2 here for the wider types - it's occasionally a hair slower (u32, f32). Is that the double-pumping, or the k-mask register overhead, or something else? Hard to tell while memory bandwidth is the dominant cost - so the next step is removing memory bandwidth from the picture entirely.

6. Taking memory bandwidth out of the equation

All of the numbers above are moving 10MB-80MB per run - well past L1 (32KB) and L2, and for the wider types past this CPU's 96MB L3 too. To isolate pure compute/instruction throughput, the fix is to shrink the buffer down to something that fits entirely in L1D and process the exact same bytes over and over (4KB, looped 4096 times per timed sample) - so every access after the first is served straight out of L1, and memory bandwidth simply can't be the bottleneck anymore:

TypeScalar (bitmask)AVX2AVX-512AVX-512 vs AVX2
u80.80 GOp/s77.8 GOp/s80.7 GOp/s+4%
u161.98 GOp/s38.9 GOp/s58.0 GOp/s+49%
u3217.6 GOp/s19.2 GOp/s29.3 GOp/s+52%
u648.86 GOp/s9.71 GOp/s14.1 GOp/s+46%
f321.60 GOp/s18.9 GOp/s34.0 GOp/s+79%
f641.61 GOp/s9.41 GOp/s17.3 GOp/s+84%

Once memory stops being the bottleneck, AVX-512 clearly and consistently beats AVX2 across every type - the near-tie (or occasional loss) in the large-buffer table really was memory bandwidth masking a genuine compute advantage. That said, the gains for u32/u64/ f32/f64 (+46% to +84%) are bigger than "double-pumping" alone should allow: if a 512-bit op genuinely cost exactly 2x a 256-bit op in execution, processing 2x the data per instruction should net out to roughly the same throughput, not a 50-80% win. The likely explanation is that double-pumping caps the execution-port throughput, but halving the number of instructions issued still halves other per-instruction costs that don't double-pump - loop overhead, decode/issue bandwidth, branch counting - and that's apparently worth a lot on this core. u8, by contrast, only gains a modest +4%, because its speedup was never coming from extra lanes in the first place at this width - it comes from the masked-fusion trick from section 3 (folding the select into the arithmetic instruction itself, saving one instruction versus AVX2's separate blend), which is a smaller, more specific win than the broader per-instruction overhead savings the wider types get. Take the precise split between these two effects with a grain of salt without deeper microarchitectural profiling (e.g. counting actual retired instructions/uops) - but the direction is clear either way: AVX-512 is a real win here, just not a clean "2x the lanes, 2x the speed" one.

7. Can't the compiler just do this for me?

Sometimes - and it's worth knowing exactly when. Disassembling both builds of this exact benchmark turned up a real difference between compilers:

  • MSVC (cl) compiled the plain scalar (bitmask) condScalarBitmask loop completely literally: one byte per iteration, plain general-purpose registers, no vectorization at all.
  • clang-cl, at the same optimization level, recognized the branchless mask/add/sub pattern in that same scalar loop and auto-vectorized it into real 4-way-unrolled AVX-512 code - despite nothing in the source calling a single intrinsic in condScalarBitmask.

Both are "correct" - but it means benchmarking "scalar (bitmask)" performance under clang-cl wasn't actually measuring scalar (bitmask) performance at all. This is exactly the trap: auto-vectorization is real and can be impressive, but it's also not guaranteed, and it's sensitive to how the loop is written. In more complex codebases - loops with unclear pointer aliasing, function calls the optimizer can't see through, non-trivial control flow, or arithmetic that doesn't have a clean saturating/ wrapping equivalent - the same auto-vectorizer can and does silently fail to vectorize, with no warning at all unless you go looking at the disassembly. Writing the intrinsics by hand is the only way to guarantee the vectorized path, in every build configuration, on every compiler.

One caveat about this benchmark's own setup: each implementation is called through a function pointer rather than directly by name (necessary to stop the repeated calls in the timed loop from being optimized away entirely - a loop calling the same pure function on the same unchanged data is otherwise a legitimate target for the compiler to collapse down to one iteration). That indirection adds a small, likely negligible, per-call overhead versus a direct/inlined call - but it doesn't change whether a given loop gets auto-vectorized, since that decision is made when the function itself is compiled, not at the call site. Disassembling the standalone lp() confirms this directly: it's vectorized into AVX-512 by clang-cl exactly as described above, even though it's only ever invoked indirectly here.

7.1. What happens with the ordinary if / else?

The previous comparison specifically used the scalar bitmask implementation. I initially interpreted the results as evidence that MSVC wasn't able to auto-vectorize this workload, but that's not quite right. Re-running the benchmark with the original if / else conditional shows that MSVC can auto-vectorize the ordinary scalar version to AVX-512 as well.

The exact result depends on the type and workload, but the important point is that the compiler is capable of recognizing the higher-level conditional directly. The explicit bitmask isn't necessary to make SIMD possible; its purpose here is primarily to illustrate the predicate → mask → select model that underlies SIMD programming.
